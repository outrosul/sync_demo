## 二、帧同步（lockstep）要点

| 知识点 | 说明 | 本 demo 现状 |

| 同步对象 | 操作指令（摇杆、放技能），不是状态 | ✅ 已实现（`MSG_INPUT` 只传按键布尔） |
| 定帧下发 | 服务端收集操作，tick 结束定帧 `frame_id` 下发 | ✅ 已实现（`MSG_FRAME` + seq） |

| 收到多帧 | 逻辑帧**加速执行**（追帧） | ✅ `logic_clock.py`（追帧） |

| 断线重连 | 从第一帧开始加速重算（免重建代码） | ✅ `disconnect_grace`（10s 宽限重连恢复身份+状态，超时真移除） |
| 防外挂 | 客户端有全部逻辑 → 难防、结算少数服从多数、1v1 无法校验 | ✅ 符合（demo 无服务端校验） |
| 补帧原则 | `Sum(delta_time) == Sum(wall_time)`，逻辑帧固定 33ms | ✅ `logic_clock.py` `missed_frames`（补帧） |
| 逻辑分层 | 核心层（各端一致）/ 表现层（渲染等本地独有） | ✅ 已实现（`core/` vs `net/` 渲染） |
| 确定性 | 随机种子一致、OrderedList、小数改整数、编译顺序一致 | ✅ 已实现（定点 `Fixed` + 显式 RNG） |

### 不同步定位（资料里的做法，重点）

- 资料做法：每个客户端把**每帧**所有单位核心属性快照发服务端记日志，战斗结束核对。
- 本 demo 等价物：`core/sync_diff.py` 的 FNV-1a hash 对比 + 逐字段定位（更轻量，
  但原理一致：都是「逐帧快照 → 事后比对」）。
- ⚠️ 差异：资料是「全文快照归档」，我们是「hash + 字段摘要」，前者能事后回溯任意帧，
  后者只能回答「哪帧不一致 + 当前字段差多少」。

## 三、状态同步（c/s）要点

| 知识点 | 说明 | 本 demo 现状 |
| --- | --- | --- |
| 编码结构 | 函数调用 ↔ 封包发送兼容（decorator hook 参数自动 pack），格式 `[opcode, params, meta]` | 我们用 JSON 行协议，更简单 |

| **移动同步公平性** | 服务端权威，网络好的一致，个人网络问题不影响他人 | ✅ 已实现（state 模式服务器权威） |
| **影子跟随 shadow** | 客户端 shadow 位置始终与服务端一致，网络波动时做位置预测 | ✅ 已实现（`ghost` 虚影 ≈ shadow） |
| **dead reckoning** | 航位推算位置预测，见下公式 | ✅ `smoothing.py` `DeadReckoner` |
| **弹性跟随** | 距离接近预测/准确位置、超阈值拉回、停止修正 | ✅ 已实现（`snap_threshold` 容差） |
| 网络大波动 | 禁止客户端移动、追帧、帧率下降 | ⚠️ 未做「禁止移动」，有追帧（`logic_clock`） |

### dead reckoning 位置预测公式（资料原文）

```
walltime_diff = (tc_cur - tc_start) - (ts_last - ts_start)
predict_pos   = last_sync_pos + speed * walltime_diff * move_dir
```

- `ts_start`：服务端开始移动第一个位置同步封包下发时间
- `tc_start`：客户端收到该封包的时间
- `ts_last`：客户端最后一次收到的准确位置封包时间戳
- 预测基于「上一次准确位置 + 速度 × 时间差 × 方向」

## 四、混合同步（dota2 方案）

- 移动封包（+仅逻辑单位创建）走帧同步，其余走状态同步。
- 动机：移动封包量大、准确性要求高，帧同步性价比高；其余逻辑开发质量可控。

## 六点五、《同步概述》

> 主题：帧同步框架接口、服务端模拟状态同步的定帧/插值/延迟，以及 For Honor / OverWatch 实战。
> 这是「预测回滚」主题最直接的一篇，与本 demo 的 `prediction.py` + frame 回滚高度对应。

### 帧同步框架（BlackBoxBase / FrameSyncServer / FrameSyncClient）

- **BlackBoxBase**：`AddCommand`（收集玩家操作上传）、`RegisterCommand`（注册命令处理函数，负数序号
  为框架保留）、`Update`（每帧逻辑，帧 tick 时调用）。—— 对应本 demo 的 `sim.InputState` + `sim.tick`。
- **FrameSyncServer**：`StartTick(random_seed, timer_interval)`（驱动帧 + 指定随机种子）、
  `StopTick`、`AddServerCommand`。—— 对应本 demo 服务器的 `_advance_lockstep` + 显式 `random.Random(seed)`。
- **FrameSyncClient**：`ReadyTick` / `Pause` / `Resume`（本地暂停 vs 全局暂停）。—— 对应本 demo
  客户端的「等帧 / 追帧」（`logic_clock.py` `FixedStepScheduler`）。
- 核心原则：**整个时间轴以服务端帧为驱动，收到一个服务端帧所有客户端步进一帧**。

### 服务端模拟的状态同步（定帧 / 插值 / 延迟）

- **定帧（fixed-step）**：某 MMO 引擎 0 缓冲靠 boost.asio 立即响应；另一种思路是消息带服务端时间戳，
  客户端按时间戳顺序还原。**不定帧难回滚**（无法把世界回滚到精确 0.123s 前，事件驱动）。
  **定帧方便回滚 + 增加确定性 + 方便比对差异（md5/容差快照）**。
- **客户端对齐服务端帧**：网络/性能导致帧堆积时，客户端加/减速追齐或等待。—— 即「等帧/追帧」。
- **渲染的插值**：逻辑 30FPS 渲染 60FPS 时，渲染落后逻辑 1 帧，用
  `0.5*(S(N)-S(N-1))` 插值（维护一个「渲染时间」）。—— 对应本 demo `smoothing.py`。
- **网络延迟**：指令去服务端转一圈 = 多 1 个 rtt；加 1 帧缓冲 = rtt+30+16ms。

**逻辑帧与渲染帧的对应关系**（渲染落后逻辑 0.5 帧，中间帧取插值）：

```text
Logic Frame  │ 1(10)  │        │ 2(20)  │        │ 3(30)  │  ...
Render Frame │ 0(0)   │ 0.5(5) │ 1(10)  │ 1.5(15)│ 2(20)  │ 2.5(25)│ 3(30) │
Render Frame │ 0(5)   │ 1(10)  │ 1.5(15)│ 2(20)  │ 2.5(25)│ 3(30)  │ ...
```

含义：逻辑帧间隔 10ms（1(10)、2(20)、3(30)…），渲染帧插在两个逻辑帧之间（0.5(5)…），渲染比逻辑
落后 0.5 帧，中间渲染帧取两次模拟结果的插值。核心 = 维护一个「渲染时间」，通过它和逻辑值插值，
快慢用时间比例缩放调整，使动作与位移精确匹配。

### For Honor（变种帧同步：隐藏网络延迟）

- 每帧除自己指令外，还会收到**其他人落后的指令** → 帧同步**回退到最远的缺失帧**再模拟。
- 需要**历史 buffer** 记录所有世界状态，每帧做回退。—— 对应本 demo `prediction.py` 的 history /
  `confirmed_world` 回滚基线。
- **技能逻辑**：状态机（KATANA）驱动，输入统一抽象成「指令」（玩家/AI 都一样）。
- **动作表现**：motion matching 简化动画状态机。

### OverWatch（预测和回滚 / 网络优化）

- **预测和回滚**：客户端本地先行预测（连续前进），指令逐帧上行；服务端落后约半个 RTT；
  结果不一致时回退到对应帧重新模拟。—— 本 demo 帧同步「本地预推演 + frame 回滚」同机制。
- **Jitter Buffer（抖动缓冲）**：指令先入缓冲队列，服务端按固定节奏消化，牺牲少量延迟换平稳推进。
- **丢包恢复**：丢包时服务端停滞等待重传，后续指令排队（重传计数 x15），恢复后继续。

**客户端预测与回滚**（本地先行，服务端落后半个 RTT）：

```text
CLIENT（绿色时间条）●━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
                     👥👥👥👥（本地预测，角色连续前进）
                      │    │    │    │    │   （指令逐帧上行发给服务端）
                      ↓    ↓    ↓    ↓    ↓
SERVER（蓝色时间条）▁▁▁▁▁▁▁▁▁▁▁▁▁（落后于客户端）
                                          | buffer | half RTT |
```

**Jitter Buffer 抖动缓冲**（指令先入缓冲队列，服务端按稳定帧率消化）：

```text
CLIENT（绿色时间条）●━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
                     👥 👥 👥 👥（指令沿对角线延迟到达）
                      ↘   ↘   ↘   ↘   ↘
SERVER（蓝色时间条）▐ buffer ▕▁▁▁▁▁▁▁▁▁▁▁▁▁▁
                    （先进入缓冲队列，再按稳定的帧率依次消化）
                                          | half RTT |
```

**丢包与恢复**（丢包时服务端停滞等待重传）：

```text
CLIENT（绿色时间条）●━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
                     👥
                      ↘ （某个指令包丢失 ✖）
SERVER（蓝色时间条）▁▁▁▁▁▁▂（模拟停滞等待）
                        👥 ✖ ✖ ✖ …（后续指令排队，重传计数 x15）
（收到重传/确认后，模拟从停滞帧继续推进）
```

### 刀剑需求背景（优先级）

1. 手感确定性 2. 公平性 3. 传播一致性 4. 防作弊 5. 即时响应

- **流量**：帧同步流量比状态同步小一个数量级，易优化；缺点=客户端模拟对重逻辑不友好
  （For Honor《8 Frames in 16ms》= 一帧内回退并做 8 帧模拟）。
- **公平性**：需要仲裁决定操作（自己模拟 or 只决定操作帧转发），网络差者不得利。
- **即时响应 vs 一致性**：矛盾——自己响应即时 = 可能错、与别人不一致；保证第三方视角一致即可。
- **防作弊**：帧同步全量模拟存在开图（可隐藏视野外单位交服务端模拟）；状态同步更统一但仍有高亮/自瞄。
- **模块低耦合**：逻辑模拟独立运行，换方案不伤筋动骨。—— 本 demo 的 `core/`（纯逻辑）正是为此设计。

## 七、《ARPG 游戏战斗同步和优化》

> 主题：状态同步的发展与迭代。这篇把「预测回滚 / 技能同步 / 时钟同步 / 插值 / 延迟补偿」
> 串成完整体系，且明确点出「延迟补偿的副作用」这一反直觉的坑。

### 1. 状态同步 vs 帧同步（对比表）

| 项目 | 状态同步 | 帧同步 |
| --- | --- | --- |
| 流量 | 相对高 | 相对低 |
| 回放 | 记录文件大 | 记录文件小 |
| 安全性 | 服务器实现逻辑，安全性高 | 逻辑在客户端，反外挂压力大，无法避免开图挂 |
| 战斗校验 | 协议加密、内存混淆；调整校验，无法彻底解决 | 服务器可重启跳战斗 |
| 网络卡顿表现 | 瞬移、回位、莫名掉血 | 战斗卡顿 |
| 服务器压力 | 大 | 小 |
| 客户端实现 | 调优状态同步，做差值处理 | 按单机开发，逻辑/表现分离；逻辑层不碰浮点、不确定顺序结构 |
| 打击感 | 相对差 | 更好 |
| 客户端性能 | 优势明显（直接裁切） | 逻辑性能优化有压力 |

### 2. 状态同步发展三阶段

- **快照同步（Quake, 1996）**：客户端纯渲染器，服务器每帧算全世界再广播快照。
  问题=带宽随对象数直线上升 → **增量快照同步**（只发变化对象）→ 按客户端定制分化。
- **客户端预测与回滚（TimeWarp 算法）**：
  1. **客户端预测**：本地移动 + 记录时间戳进 **MOVE BUFFER**（滑动窗口）+ 发服务器。
  2. **服务器校验**：合法则应用+广播；不合法则纠正+下发。
  3. **客户端回滚**：收到服务器位置，与预测一致则删 MOVE BUFFER 该指令；不一致则
     **回滚到服务器认可位置 + 重放 MOVE BUFFER 后续指令**，再用插值平滑修正。
  - UE5 对应实现：`ReplicateMoveToServer` / `ServerMove` / `ClientAdjustPosition` /
    `ClientUpdatePosition`（收到校正后先回滚、再重放 PendingMove）。
  - **信任主控客户端**：ARPG 倾向信任主控，服务器按估测时差/延迟预计其当前状态广播；
    校正时「小偏差不动、剧烈偏差直接跳」。

  **TimeWarp 时序（客户端 = 本地先行预测，服务器 = 校验回 ACK/NAK）**：

```text
                          时间 ────────────────────────────────►
   客户端                                                        服务器
     │  初始: Pos(0,0,0)                                           │  初始: Pos(0,0,0)
t1   │  本地执行 "0ms MoveForward"  → Pos(1,0,0)                    │
     │ ════════ 发送: 0ms MoveForward ═════════════════════════►   │
t2   │                                              服务器执行移动:   │
     │                                              Pos(0,0,0)→Pos(1,0,0)
     │ ◄════════════ 回发: ACK Move 0ms ══════════════════════════ │
t3   │  本地执行 "70ms MoveRight" → Pos(1,1,0)                       │
     │ ════════ 发送: 70ms MoveRight ═════════════════════════►    │
t4   │ ◄═══════ 收到 ACK Keep Pos(1,1,0)（一致，无需回滚）═══════ │
     │                                              服务器校验:       │
     │                                              Pos(1,0,0)  ✗ 不合法
t5   │  本地执行 "120ms MoveForward" → Pos(2,1,0)                    │
     │ ◄═══════ 回发: NAK Move 70ms  Pos(1,0,0)（否决 70ms 那步）═══ │
t6   │  本地当前 Pos(2,1,0)，收到 NAK → 回滚到 Pos(1,0,0)            │
     │  重放 "120ms MoveForward" → Pos(2,0,0)                        │
     ▼                                                             ▼
```

  图解：客户端每步本地先行（MoveForward/MoveRight），把带时间戳的移动发给服务器；服务器校验，
  认可回 ACK（绿色）、不认可回 NAK（红色，指出应回退位置）；客户端收到 NAK 回滚到认可位置、
  重放 MOVE BUFFER 后续指令，最终双方收敛到一致（Pos(2,0,0)）。
- **玩家技能同步**：客户端请求 → 服务器验证（资源/冷却）→ 通过则执行+Multicast 广播技能事件
  → 客户端重置状态、播放表现、本地预测技能效果（最终以服务器为准）。

### 3. 关键问题及解决

- **时钟同步**：客户端时间戳请求 → 服务器回时间戳 → 算延迟=往返/2、时差=本地-服务器+半延迟；
  多次采样取中位数、丢弃超标准差/中位数1.5倍的样例（过滤 TCP 重传）。
- **插值（Interpolation）/ 外推（Extrapolation，Dead Reckoning）**：
  第三方玩家始终朝「最新收到的状态」插值；没新包时按上个移动包继续运动（外推），
  收到新包再校验纠偏。纠偏：距离远则瞬移、近则三次样条插值、加速时加二阶参数（加速度）。
- **延迟补偿（Lag Compensation, Valve 2001）**：服务器记录过去 ~0.5s 世界，收到攻击请求时
  「倒带」到该玩家延迟对应的历史状态判定命中，再同步结果 → 网络差者所见即所得。

### 4. 延迟补偿的副作用（重要！）

> 延迟补偿并非普遍适用，采用与否取决于游戏类型。副作用：若击杀时间极短（一击必杀），
> 低延迟玩家 A 先开枪、高延迟玩家 B 后开枪，服务器先处理 A（B 已死）；但 B 的请求 200ms 后
> 才到，服务器「倒带 0.2s」到 A、B 都未死亡时，B 的攻击也判有效 → **A 也死**。
> 结论：延迟补偿下，**高延迟玩家反而因补偿获得更有利判定，损害低延迟玩家体验**。

## 八、《网络同步》

> 2022 年技术分享。

### 8.1 同步的概念与延迟

- **控制端**：驱动状态变化/事件的源头；**表现端**：接受状态/事件做表现反馈。
- **手感** = 输入与期望反馈一致且及时。
- **延迟来源**：输入延迟（触屏 ~40ms）· 逻辑处理（ClientTick 33ms / ServerTick 100ms）·
  网络传输（50~200ms，丢包在可靠传输下≈加延迟）· 逻辑→渲染帧延迟。
- **感官约束**：手眼延迟 >120ms 操作端反馈粘滞；延迟感受基于真实物理时间，与位移速度和对抗节奏相关。

### 8.2 一致性、确定性与性能

- **一致性**：本地写需求（类比多人协作的 arbiter/participant 模型），本地与远端冲突时修正难
  （位移突变、朝向突变、动作切换、滑步、射击命中、碰撞穿插、静态物体永久状态）。
- **确定性**的坑：本地时钟一致性、随机数（固定 seed）、System timestamp、非序容器遍历
  （hashTable 按指针 hash）、浮点数学、Callback 时机、逻辑帧率（插值/截断误差）。
- **性能**：Server 完整模拟开销大（骨骼动画/物理/内存）；Client 全量模拟受最低端设备基线制约。

### 8.3 帧同步 vs 状态同步（对照表）

| 维度 | 帧同步 | 状态同步 |
| --- | --- | --- |
| 原理 | 向 arbiter 同步操作，arbiter 下发 step+操作，各端本地模拟 | 单点模拟，下发状态关键帧，接收者插值还原 |
| 优点 | 像单机开发、视觉流畅、NPC 多时流量优 | 接收端无影响、插值即可不需模拟、天然反作弊 |
| 缺点 | 一致性难、状态恢复难、难本地先行、信息公开、反作弊难 | 复杂动画难平滑、CS 逻辑分支复杂、AI 多流量大、Server 模拟贵 |
| 改进 | Debug 工具链、断线重连、验证服、预测+Rollback | 部分退化成指令同步、主控客户端模拟 |
| 适用 | ≤6 人竞技/体育/格斗（war3/dota1、王者、实况、街霸5） | 大多数多人游戏 |
| 代表作 | 王者荣耀、街霸5 联机 | — |

### 8.4 状态同步的同步类型

对象的创建/销毁 · RPC 调用 · Property 同步 · Locomotion 同步。

**C/S 架构的上报 / 下发链路**（客户端操作上报 → 服务器 tick 模拟 → 序列化 → AOI 过滤 → 下发）：

```text
Client操作或状态上报 ──┐                    ┌─ 主控Client的阻断或屏蔽（可选项）
Client操作或状态上报 ──┤                    │
        │ (Server平滑Buffer 可选)            ▼
        ▼                          发送到每个有待发网络包的Client
Server Tick 模拟/修改状态                    │
        │                                   ▼
        ▼                          观看者Client执行属性变化
Push到计算本地entity的消息队列Buffer ◄── AOI系统过滤接收者
        │                                   ▲
        ▼                                   │
Server Tick 序列化每个entity的变化和RPC ◄── AOI Tick 更新每一个对象的
                                            增/关注，授权客户端集合
```

**上报链路**（客户端 → 服务器）：客户端操作/状态上报 →（可选 Server 平滑 Buffer 削峰）→
Server Tick 模拟修改状态 → 序列化 entity 变化 + RPC → Push 到消息队列 Buffer。
**下发链路**（服务器 → 客户端）：AOI 系统过滤接收者（AOI Tick 更新授权客户端集合）→
（可选中主控 Client 阻断/屏蔽）→ 发送到有待发网络包的 Client → 观看者 Client 执行属性变化。

### 8.5 物理同步（重点，与本 demo 高度相关）

- **确定性帧同步**：Fixmath32 定点数学库、compact_dict/ordered_set 容器、定点 Wichmann Hill
  随机数、定点 Box2D、严格时序 logic entity、帧号定点 timer。
  - 代价：定点性能慢、改引擎工作量大、场景数据重导、数值范围有限（坐标 ~1000）。
- **内插值（Interpolation）**：只同步位置(12B)+旋转(16B)，不立刻应用、多等一个包、在过去两个
  状态间按时间差线性插值；引入 2×ping 延迟。问题：高速反弹等大幅改变时表现与频率强相关、连续
  丢包会停半空 → 按收包间隔在内插/外插间切换。
- **外插值（Extrapolation）**：收到状态包立即应用 + 用线速度推断下一步轨迹（降低到 1×packet 延迟），
  可用 Dead Reckoning 优化。问题：碰撞时（不知道对方信息）推测全错 → 本地跑物理引擎预测+状态修正。
- **Source 引擎**：两类物理对象——服务端完全控制 / 仅本地运行（细小装饰物）。
- **火箭联盟全预测**：两端各跑物理引擎，客户端不等待服务器一路前向；维护输入缓冲区，收包后按帧号
  对比，失败则回滚到该帧+应用服务器数据+连续仿真追到当前。核心 = 确定性（状态+N 指令=新状态）。
- **分布式授权**：谁拿球谁主控（本地几乎零延迟），以容忍作弊+多耗带宽换低延迟，适合 VR/少人。

### 8.6 网络现状与 KCP

- 国内 4G/骨干网稳定（同城 8ms、杭州↔广州 50ms），丢包率 <2%。
- 海外：广州↔北美 ~200ms，15% 玩家丢包 1~5%，3% 超 10%，烂网络 30% 延迟 >100ms。
- **UDP**：TCP 过于保守、UDP 精细化控制且短快；缺点=高峰被优先丢、1~2% 连不上、部分运营商不支持。
- **KCP**：UDP 上的可靠传输；延伸参考《挖掘 UDP 传输的潜能》（内部课程）。

| 手眼延迟 120ms 粘滞阈值 | ❌ 可做「延迟-手感」对照实验 |

## 八点五、《某 ARPG 魔神编辑器（战斗部分）实现分析》

> 主题：技能同步的工程实现（状态同步 + RPC + Property 属性同步）。
> 与本 demo 的关系：讲的是「技能释放 / 位移 / 伤害」三级同步，其中「主客户端先行 vs 服务端先行」
> 的选择，直接对应我们 frame/state 两种模式的手感权衡。

### 同步机制核心

- **主角技能 = 主客户端先行**：玩家输入 → 主客户端逻辑（先行 PushGraph 播放动作）→ RPC 服务端
  （结算 + 广播）→ 从客户端逻辑（表现）。即「本地先行动，服务端权威结算」。
- **怪物技能 = 服务端先行**：AI 输入 → 服务端逻辑 → 客户端表现。服务端权威、客户端纯表现。
- **位移同步**：技能位移期间客户端 Graph 驱动 Entity 位移，**不接受 motionPacket 位置校正**（保证流畅）；
  需 RPC 通知服务器「解除速度限制」防止超速反作弊拉扯。位移结束后用 motionPacket 插值修正。
- **伤害同步**（两种）：
  - 服务器结算下发：攻击盒/法术场/子弹 → `calcSkillResult` → 结算模块 → HP 属性同步 + RPC 下发结果。
  - 客户端结算上报：子弹/射线碰撞 → 客户端检测命中上报 → 服务端 **onBulletHitWrapper 校验** → 结算下发。

**技能位移同步时序**（主客户端 → 服务器 → 从客户端，位移期间不接受位置校正）：

```text
主客户端                    服务器                     从客户端
  │                          │                          │
  │──上报位置信息(每0.1s)────→│                          │
  │                          │──广播位置信息─────────────→│
  │──上报位置信息────────────→│                          │→ 位置插值模拟
  │                          │                          │
  │──发送技能RPC─────────────→│                          │
  │                          │──广播技能RPC──────────────→│
  │  ┌──────────────┐        │                          │  ┌──────────────┐
  │  │ 播放技能位移  │        │                          │  │ 播放技能位移  │
  │  │ graph        │        │                          │  │ graph        │
  │  └──────────────┘        │                          │  └──────────────┘
  │──上报位置信息────────────→│                          │
  │──上报位置信息────────────→│                          │
```

关键点：① 技能位移期间客户端 Graph 驱动位移、不接受 motionPacket 位置校正（保证流畅）；
② 位移期间速度大，需 RPC 通知服务器解除速度限制防超速反作弊拉扯；③ 主/从客户端分别播放 graph
驱动位移 → 位置非强一致，位移结束后用 motionPacket 插值修正。

## 八点六、《从零开始的同步机制探索》

> 主题：同步机制的通用调研，重点讲「网络延迟处理」——预测/纠错、缓存池、倒带法。
> 这篇把「预测 vs 缓存池」和「倒带法副作用」讲得最清楚，是本 demo 网络延迟模块的关键参考。

### 1. 帧同步两种模式

- **传统模式**：客户端上传指令 → 服务端转发后才生效。适合操作连贯、写实的游戏（足球）。
- **预测回滚模式**：客户端本地立即执行指令 + 上传，发现不同步再回滚。适合有效输入少、动作不连贯、
  不太写实的游戏（拳皇）。
- **核心**：追求客户端表现一致、数据量少、客户端含全量信息（反全图挂难）。
- 关键问题：① 环境一致（初始态/时间间隔/随机/无浮点/哈希遍历顺序一致）；② 缺帧怎么办
  （大部分帧同步**只做表现预测**——模型先走、逻辑位置原地、卡顿等帧）；③ 防作弊（服务端跑同逻辑
  比对 / 客户端互比 / 战局回放举报）。

### 2. 网络延迟处理（位置同步，帧/状态通用）

- **预测与纠正**：B 预测 A 的操作 pv，收到服务端真值 v 发现不等时纠错。两种纠错策略：
  - ① 用 N 帧缓慢插值纠正（如 5 帧）→ 平滑但滞后、轨迹拖尾；
  - ② 用 1 帧立即纠正 → 快但突跳、顿挫。
  - 可「提前一帧纠正」或「延长纠正时长」。
- **缓存池（延迟换稳定）**：真实网络延迟不稳，B14 帧可能啥都收不到。帧同步「过多预测会导致
  客户端环境不一致」，故用**缓存池**——收到的帧先入缓存，渲染从缓存取、恒定慢一帧执行。
  **一帧缓存的代价 = 一帧延迟**。300ms 缓存池能吸收 0–300ms 延迟波动 → 整体慢 300ms 但平滑连续。
- **倒带法（服务端，状态同步）**：服务器记录过去 ~0.5s 世界，收到延迟玩家的请求时调取
  「0.2s 前」状态判定再同步 → 玩家所见即所得。

**网络波动断档示意**（B14 帧没数据 → 掉帧）：

```text
 客户端A      │ 10    11    12    13    14    15    16 │
              │  ╲     ╲     ╲     ╲     ╲             │   ← 操作到达服务端时间忽快忽慢
 服务端       │ 11    12    13    14    15    16    17 │
              │  ╲     ╲     ╲     ╲    ╲              │
 客户端B      │ 10    11    12    13   ？14   15    16 │
              │                          ↑             │   ← 第 14 帧没收到数据
 客户端B渲染  │  …     12    13    ✗     15    16      │      渲染无米下锅
```

**增加一帧缓存后的帧流转**（缓存池吸收波动）：

```text
 客户端A      │  9    10    11    12    13    14    15    16 │
 服务端       │ 11    12    13    14    15    16    17    18 │
 客户端B      │ 10    11    12    13    14    15    16       │  ← 收到帧
 客户端B缓存  │ 10    11    12    13    14    15    16       │    先入缓存池
 客户端B渲染  │  …     11    12    13    14    15   …        │  ← 渲染从缓存取，恒定慢一帧
```

**服务端倒带法流程示意**：

```text
  有延迟的玩家 (200ms)                     服务器
    │                                       │ 持续记录过去一段时间内
    │                                       │ (比如 0.5 秒) 游戏内的所有信息
    │  玩家在其屏幕上所见的位置发起操作        │
    │ ════ 请求 (延迟 200ms 到达) ════════► │
    │                                       │ ① 倒带：调取 0.2 秒前的状态
    │                                       │ ② 在该状态下进行判定
    │                                       │ ③ 判定结果同步给所有客户端
    │ ◄════════════ 判定结果 ══════════════ │
    │                                       │
    │  效果：操作虽有延迟，但开枪/操作时       │
    │  所见画面一致                          │
```
  **副作用（关键）**：延迟补偿/倒带让**高延迟玩家拖累低延迟玩家**——一击必杀对射时，
  B（200ms）的攻击倒带后也判有效，导致已开枪的 A 也被判死。若不平滑处理，高延迟玩家
  反而获得有利判定。

## 八点七、《弱网自适配优化方案》

> 主题：**方法论层面**——不单实现某个机制，而是「批量模拟弱网环境 → 跑测预设方案 →
> 统计延迟 → 反推最优策略（并可上强化学习）」。对本 demo 的启示是「把故障注入 + 延迟统计
> 做成可批量跑测的自动化闭环」。

### 1. 环境模拟（三级 分级）

- **网络分级**（用 clumsy/NetAir 模拟，本 demo 已有 `fault.py` 的对应参数）：
  - 极好：50Mbps / 7ms / 0% 丢包
  - 良好：5Mbps / 50ms / 1% 丢包
  - 一般：2Mbps / 150ms / 2% 丢包
  - 差：150kbps / 1500ms(?) / 10% 丢包
  - clumsy 支持的故障函数：Lag / Drop / Throttle / Duplicate / Out of order / Tamper / RST / Cap
    —— 本 demo `fault.py` 已覆盖 Lag(延迟)/Drop(丢包)/Duplicate(重复)/Out of order(乱序)/Throttle(带宽)/
    Jitter(抖动)，缺 Tamper/RST 两项。
- **设备分级**：性能（收发包效率 → 时延）+ 系统兼容性。
- **输入分级**：录像模式（存输入复用）vs AI 模式（覆盖更多场景）。

### 2. 预设方案（协议 + 冗余编码）

- **协议选择**：TCP（可靠稳）+ 延迟高；UDP（低延迟）+ 不可靠；KCP（自适应可靠 UDP）+ 复杂。
  可调参数：TCP 初始拥塞窗口/重传超时；KCP 发送接收窗口/超时重传/tick。
- **冗余编码**：XOR（一份冗余）/ DUP（重复编码）/ RS（Reed-Solomon，任意份冗余，前向纠错）。
  用控制变量法形成不同预设方案。

### 3. 数据统计（埋点）

- 环境描述（kbps/latency/drop/device/cpu/os）
- 选择方案（protocol/tick/rc 冗余编码/n/k/reliable）
- **延迟埋点**：客户端输入产生 → 发送 → 服务端接收 → 转发 → 客户端接收&消耗，各节点耗时，比赛结束上传。

### 4. 自动化跑测 + 强化学习

## 八点八、《弱网移动同步优化》

> 主题：**实践课题**，从四个方向研究弱网移动同步体验——抖动平滑、移动预测、
> 自适应 FEC（GRP）、双通道。前两个正是「缓存池」与「移动预测」的核心落地。

### 1. 抖动平滑（MMO 弱网）

- **现象**：15% 丢包下，本地看到的远端移动「中间突然停下来再继续」——因为帧缓存容器
  数据用完了。
- **目标**：20% 丢包 / 200ms 短延迟下仍流畅（无解，只能优化体验 + 设基线）。
- **方案（动态调节闭环）**：
  - 丢包/延迟 → 帧缓存减少 → **减小插值速度**；
  - 帧缓存恢复 → **增大插值速度**（回到上一状态）；
  - 帧缓存耗尽 → **移动预测** 或 **停止移动**。
  - 核心是**通过改变插值参数 t 改变插值速度**，让缓存始终留有余量、不耗尽。
- 关键公式：`t = Δt − (p + ∇p) × α`（α=已消耗帧缓存），`P1 = P0 + (frame2.p−frame1.p)×t/(frame2.t−frame1.t)`。

**抖动平滑处理流程图**：

```text
            ┌──────────────┐
            │ 丢包或者延迟   │
            └──────┬───────┘
                   ▼
            ┌──────────────┐     ┌──────────────┐
            │  帧缓存减少    │◄────│  增大插值速度   │
            └──────┬───────┘     └──────▲───────┘
                   ▼                    │
            ┌──────────────┐     ┌──────┴───────┐
            │  减小插值速度  │────►│  帧缓存增加    │
            └──────────────┘     ├──────────────┤
                                 │  帧缓存耗尽    │──┬──► 移动预测
                                 └──────────────┘  └──► 停止移动
```

**插值速度公式**（抖动平滑核心）：

```text
  Δt = 当前帧的时间 − 上一帧的时间
  p  = 最近两次收到数据的时间差 − 1/期望帧率
  α  = 已消耗的帧缓存大小 ( Σ(k=0..n) frame_k.t )
  t  = Δt − (p + ∇p) × α      ← 调节量（通过改变 t 改变插值速度）
  P1 = P0 + (frame2.p − frame1.p) × t / (frame2.t − frame1.t)
```

### 2. 移动预测（MOBA 弱网）

- 基本链路：客户端发移动指令 → 服务端模拟 → 客户端跟随服务端下发位置。
- 预测：移动开始/转向/停止指令发出后，**延迟半个 RTT** 才被服务端处理；客户端预测位置 =
  `上次同步位置 + 上次同步方向×帧间隔×速度 + Σ(半个RTT前摇杆方向×帧间隔×速度)`。
- 用 clumsy 模拟 200ms 延迟 + 20% 丢包。优点=移动先行半个 RTT 减少卡顿；缺点=频繁转向/延迟波动大时预测不准。

### 3. 自适应 FEC（GRP）

- **FEC**：原始数据拆 M 份 + K 份冗余 = N 份发送，收任意 M 份即还原。
- **GRP**：按丢包率自适应选 N、K 和编码方式（优化固定 FEC 在好网下的无用流量）。
- 链路：`logic → kcp → grp → socket`（GRP 在 kcp 与 socket 之间）。
- 丢包率统计：分 s1/s2/s3 三段（卡尔曼滤波 + 平滑），按消息分组统计。
- 编码选择：XOR（K=1）/ DUP（M=1）/ RS（范德蒙矩阵）/ 直接发包无编码，按 N、K 支持依次选。
- 冗余后丢包率：`Σ C(N,i)·p^i·(1-p)^(N-i)`（i 从 N−K+1 到 N）。

### 4. 双通道（移动网络 + wifi）

- **定义**：两条连接同时收发相同数据，逻辑层去重保序。
- 优点：显著降低断线率/丢包/延迟波动；缺点：双倍流量（可评估通道择优发送改进）。
- 方案1「双 connection」：逻辑层实现、改动小、需消息去重（序号）；两倍流量。
- 方案2「单 connection 双 socket」：KCP 自带去重保序、流量少；但引擎改动大、风险高。
- 收发：发送时序号+1 写头部，两通道同时发；接收时按「期望序号」比对，相等上送、不等丢弃。

## 八点十、《从零开始制作基于帧同步的多人弹球》

> 主题：纯 pygame 帧同步弹球 demo，网络 + 物理两大块。与本 demo 定位最接近的一篇。

### 关键知识点

- **网络**：IO 多路复用 + 基于 UDP 的可靠传输；每客户端 TCP+UDP 两条连接（UDP 鉴权）。
- **冗余发包**：数据拆多个小包，附带其它包数据**对抗弱网丢包**，冗余数量**按丢包率动态调整**。
- **JitterBuffer**：客户端一帧收到 0~多帧，服务器帧不稳定 → 掉帧/追帧。做法：计算一段时间收到帧
  的延迟、**取最大值作为延迟时间，缓存足够覆盖该延迟的帧**；延迟跳变时**按延迟差缓慢调整到目标
  延迟值**（渐趋稳定）。结论：需按实际调参。
- **定点数（深入）**：浮点**不满足结合律**，`(x+y)+z ≠ x+(y+z)`（例 x=1e30, y=−1e30, z=1）；
  编译器/CPU 乱序执行的结合顺序不同 → 跨平台不确定。做法：数值放大 1000000 倍用整数算
  （精度 1e-6，Python 大整数不溢出）。开方用牛顿迭代、三角用泰勒展开（向量计算可替代三角）。
- **碰撞检测**：圆形暴力 O(n²) 两两比较；问题=O(n²) 效率 + 高速穿透（跨帧穿过）。
- **碰撞响应**：一维/二维弹性碰撞（动量+能量守恒）→ Impulse-based（角动量、力矩、摩擦
  Coulomb friction model）。圆形碰撞质心对质心 = 点到点，加摩擦才有旋转。

**弹性碰撞公式**（物理部分核心）：

一维弹性碰撞（动量守恒 + 能量守恒）：

```text
  动量守恒:  m1·v1 + m2·v2 = m1·v1' + m2·v2'
  能量守恒:  (1/2)·m1·v1² + (1/2)·m2·v2² = (1/2)·m1·v1'² + (1/2)·m2·v2'²
```

二维弹性碰撞（速度分解成「平行/垂直于碰撞法线」两分量，垂直方向等价于一维）：

```text
  v1' = v1 − (2·m2 / (m1+m2)) · ( ⟨v1−v2, x1−x2⟩ / ‖x1−x2‖² ) · (x1−x2)
  v2' = v2 − (2·m1 / (m1+m2)) · ( ⟨v2−v1, x2−x1⟩ / ‖x2−x1‖² ) · (x2−x1)
  其中 ⟨·,·⟩ 为向量点积，‖·‖ 为向量模长
```

Impulse-based 碰撞响应（含角动量 / 力矩，I 为转动惯量）：

```text
                 −(1 + e) · (v_r · n̂)
  j_r = ─────────────────────────────────────────────────────
        m1⁻¹ + m2⁻¹ + ( I1⁻¹(r1×n̂)×r1 + I2⁻¹(r2×n̂)×r2 ) · n̂
```

**定点数的「为什么浮点不可靠」**：浮点不满足结合律，`(x+y)+z ≠ x+(y+z)`。
例 x=1e30、y=−1e30、z=1 时 `(x+y)+z=1` 而 `x+(y+z)=0`。编译器/CPU 乱序执行的结合顺序
不同 → 跨平台结果不同。故数值放大（如 ×1000000）用整数算，开方用牛顿迭代、三角用泰勒展开。

## 八点十一、《帧同步手感优化》

> 主题：帧同步下「降低延迟提升手感」——输入层、预测回滚、**预测不回滚**三种方案。

### 1. 输入方面（6 点）

降低延迟（输入模块从黑盒提出直接轮询）、支持预测回滚、序列化/反序列化、方便统计/编码定制、

```python
                     'entities_index': update_list, consts.SHAPSHOT_PART_RECOVER: True}
    passkey = ['entities_snapshot', 'entities_index', 'md5']
    for key in verify_snapshot:
        if key in passkey:
            continue
        elif key not in client_md5_snapshot or verify_md5_info[key] != client_md5_snapshot[key]:
            diff_snapshot[key] = verify_snapshot[key]
    return diff_snapshot
```

### 3. 预测不回滚（关键！）

- 预测回滚需「高预测成功率 + 全量快照恢复耗时低」，复杂/人多项目难做到。
- 但**预测才是优化手感关键，回滚只是预测失败才需要** → 能否「只预测、不回滚」？
- 思路：借状态同步对比——帧同步逻辑黑盒 ≈ 状态同步的「服务器」，预测逻辑 ≈ 状态同步的「客户端」。
  发起操作后：部分指令发核心逻辑，预测逻辑**先行 tick** 直接驱动表现；核心逻辑 tick 后与预测逻辑
  **数据对比/更新**，据此对表现逻辑做**插值/纠正**（而非整体回滚）。
  —— 本质：把「预测失败即回滚」软化为「状态同步式的插值纠正」，适合移动预测这类「部分先行」逻辑。

### 4. 追帧 + snapshot 跳转

- 客户端逻辑帧号远小于服务端帧号 → **追帧**（多跑几遍 UpdateFrame）。
- 协议带逻辑帧号 + 时间戳 + 子命令，算网络延迟。
- 拿「几帧前」数据 → 对 actor 状态做 snapshot（不必每帧，隔几帧做）；恢复走「最近 snapshot + UpdateFrame」。
